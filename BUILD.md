# Сборка ночного агента

Порядок, в котором сборщик строит ночного агента с нуля. Новый агент собирается в новой папке и в новом репозитории. Код существующих систем владельца за основу не берётся.

Сначала контроль (история, запреты, проверки), потом возможности, самостоятельность последней. Каждый этап — один плейбук.

## Блоки

Этапы идут блоками. Внутри блока сборщик проходит этапы подряд, не дожидаясь владельца, если приёмка этапа пройдена целиком. Владелец смотрит работу и выносит контрольный блок один раз, в конце блока.

| Блок | Этапы | Что даёт |
|---|---|---|
| A. Контроль | 01a, 02, 03, 04 | запреты, шлюз, роли |
| B. Работа | 05, 06, 07 | код, запись, ночная смена |
| C. Знания и проверка | 08, 09 | база знаний, проверка целиком |

Внутри блока:

- каждый этап в своей ветке `stage/<номер>-<имя>`, следующая ветка — от предыдущей;
- после каждого этапа сборщик сам проходит его приёмку;
- любая проверка не пройдена или нужен ответ владельца — сборщик останавливается и печатает контрольный блок с тем, что успел;
- шаги, которые плейбук отдаёт владельцу (например, утвердить политику), сборщик просит выполнить и ждёт; это не конец блока.

В конце блока сборщик заполняет один отчёт по `playbooks/REPORT.md` на весь блок, с контрольным блоком в конце.

## Этапы

| # | Этап | Плейбук | Что появляется | Готово, когда | Состояние |
|---|---|---|---|---|---|
| 1 | Репозиторий | `playbooks/01-repo` | папка агента, локальный git, структура, хуки | первый коммит есть, хуки ловят секрет и push | есть |
| 1a | Хуки с LF | `playbooks/01a-gitattributes` | `.gitattributes` для уже собранных репозиториев | хуки хранятся с LF | есть |
| 2 | Политика и старт | `playbooks/02-policy` | правила «сначала всё запретить», проверка при старте | без файла политики агент не стартует | есть |
| 3 | Шлюз инструментов | `playbooks/03-gateway` | права по ролям, маскировка секретов, пометка чужого текста | атаки из набора на шлюз не проходят | будет |
| 4 | Роли | `playbooks/04-roles` | роли из `agents/` в механизме харнесса | каждая роль видит только свои инструменты | будет |
| 5 | Брокер kernel | `playbooks/05-broker` | запуск через брокер, разбор кода, гейт сложности, хеши | опасная ячейка без хеша не запускается | будет |
| 6 | Модуль записи | `playbooks/06-writer` | `save_table`, `recreate_table`, `drop_table`, реестр | запись вне префикса отклоняется | будет |
| 7 | Ночная смена | `playbooks/07-night` | список на ночь, паспорт прогона, план задачи, утренний отчёт | одна учебная задача проходит ночь целиком | будет |
| 8 | База знаний | `playbooks/08-knowledge` | публикатор, уровни доверия, поиск | проверочный набор поиска даёт базовую цифру | будет |
| 9 | Проверка целиком | `playbooks/09-evals` | набор атак, проверочные задачи, pass^k | все атаки отклонены, задачи проходят | будет |

Кокпит собирается после этапа 7, когда есть что показывать. Его раздел `blueprint/07-cockpit.md` ещё в работе.

## Правила сборки

- Один этап — одна ветка git. Один блок — один отчёт по `playbooks/REPORT.md`.
- Плейбук, которого ещё нет (состояние «будет»), не выполняется по догадке. `НУЖНО УТОЧНИТЬ`.
- Всё, что зависит от окружения, берётся из `config/local.env` нового репозитория. В репозиторий значения не попадают. Какая переменная нужна к какому этапу — в `config/local.env.example`; пустая переменная не мешает этапам, которым она не нужна.
- Версия шаблона, по которой собран этап, записывается в файл `TEMPLATE_VERSION` нового репозитория (коммит этого репозитория).

## Где что лежит после сборки

```
<ПАПКА_АГЕНТА>/
├── AGENTS.md            для сборщика: как устроен этот репозиторий
├── constitution.md      копия из шаблона; агенту только на чтение
├── TEMPLATE_VERSION     коммит шаблона, по которому собрано
├── config/
│   ├── harness/         конфиг харнесса: профили «ночь», «день», «выключен»
│   ├── policy/          правила шлюза
│   ├── allowed_remote.txt  адрес внутреннего репозитория для push; пусто — push запрещён
│   └── local.env.example   список переменных окружения без значений
├── agents/              роли в формате харнесса
├── skills/              свои скиллы
├── src/
│   ├── gateway/         шлюз инструментов
│   ├── broker/          брокер kernel, разбор кода, гейт сложности
│   ├── writer/          модуль записи
│   ├── orchestrator/    ночь: готовность, паспорт, задачи, отчёт
│   └── publisher/       база знаний
├── tests/
├── evals/               атаки, проверочные задачи
├── docs/decisions/      решения сборщика и владельца
├── tools/hooks/         git-хуки
├── knowledge/           база знаний
└── runs/                прогоны и журналы; в git не попадает
```

Язык кода — Python, кроме тонких частей, которые харнесс требует писать на своём языке (например, плагин). Такая часть только передаёт вызов в Python-модуль.
