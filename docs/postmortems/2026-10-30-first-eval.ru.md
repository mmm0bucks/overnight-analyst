# 2026-10-30 — первая оценка: потерялся ход на исправление JSON

[English](2026-10-30-first-eval.md) · **Русский**

**Последствия.** В первом `overnight eval --runs 3` этап analyze в прогонах 1 и 2 упал
одинаково, поэтому оба закончились `partial` без результатов по гипотезам.

**Что произошло.** Analyze потратил 5 SQL-запросов за два первых хода (4 проверки
заложенных ошибок и свой запрос для H5), потом ещё несколько раз просил `run_sql`, хотя его
уже не предлагали. На последнем ходу ответил битым JSON. Просьба исправить JSON ушла, но
ходов не осталось, и этап упал. Повторилось в 2 прогонах из 2.

**Причины.** Исправлению, которое выпало на последний ход, негде было случиться. Квота 5
запросов мала для 5 гипотез и одной проверки.

**Исправления.**
* Исправлению JSON всегда достаётся свой ход (`agent.run_stage`).
  Тест: `test_bad_json_on_last_turn_still_gets_a_repair`.
* Квота SQL на этап 5 → 8.

**Найдено по ходу, тоже исправлено.** Счётчик расхода ключа записывался один раз, в конце
прогона, поэтому прерванный на середине прогон не учёлся бы. (Здесь этого не случилось:
сначала я ошибочно принял ещё идущую оценку за прерванную.) `Metered` теперь сохраняет
расход после **каждого** вызова модели. Тест: `test_spend_is_saved_after_every_call`.

## Повторная оценка после исправления

3 прогона, 3× `ok`, **15 из 15** гипотез верно, 49–65 тыс. токенов на прогон. В одном
прогоне collect получил от модели испорченный JSON (`"sources": ["S": [], "sources": ["S7"] ...`) —
ход на исправление его поймал, прогон закончился `ok`. Это стало видно благодаря полю
`near` в событии `repair` (добавлено после первой оценки).
