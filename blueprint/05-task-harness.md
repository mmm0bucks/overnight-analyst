# Ночная смена и длинные задачи

Как агент получает работу на ночь, ведёт задачу по шагам и сдаёт её утром.

## Ночь по порядку

1. **Проверка готовности.** Код проверяет, что доступно: модель, шлюз инструментов, kernel, SQL, остаток жизни учётных данных. Результат — набор доступного, а не «да или нет».
2. **Паспорт прогона.** Код собирает паспорт: что можно читать, куда писать, какие инструменты, до скольки работать, бюджет токенов.
3. **Список владельца.** Агент берёт задачи из списка на ночь по порядку.
4. **Самостоятельный выбор.** Если время и бюджет остались — задачи владельца из трекера (К19).
5. **Финал.** Код собирает итог по артефактам и пишет утренний отчёт.

Если вычисления недоступны, агент не закрывает ночь как сбой. Он делает работу, которой хватает доступного: разбор задач, планы, база знаний.

Если владелец выключил агента, ночь не стартует, в журнале причина «выключен владельцем».

## Список владельца на ночь

Файл `tonight.md` в рабочей папке. Владелец заполняет его днём.

```markdown
## Задача 1
Цель: <что должно получиться, одной фразой>
Готово, когда: <проверяемый признак: таблица, число, файл>
Данные: <какие источники можно читать>
Запись: <какие таблицы агента можно создать; «нет», если не нужно>
План: plan.json одобрен, хеш <первые 8 символов>
```

Правила:
- Задачи делаются по порядку. Следующая — после того, как предыдущая закрыта или остановлена с причиной.
- Задача без одобренного плана делается как самостоятельная: только чтение и черновик плана.
- Если цель или критерий непонятны — `НУЖНО УТОЧНИТЬ` в отчёт, задача пропускается.

## Самостоятельный выбор

Когда список владельца закончился, агент выбирает задачи сам.

- Только задачи владельца в трекере. Чужие не берёт.
- Приоритет: срок ближе → дольше без движения → меньше работы до результата.
- Не больше двух задач за ночь.
- Что можно: читать задачу, вики, данные; исследовать; написать разбор и черновик плана.
- Чего нельзя: записывать в кластер. План не одобрен владельцем (К19).
- Результат — черновик плана в утреннем отчёте. Владелец одобряет его днём, и задача может попасть в список на следующую ночь.

## План задачи

Для каждой задачи планировщик пишет `plan.json` в папке задачи.

```json
{
  "task": "Повторные отклики в октябре",
  "goal": "Таблица первых откликов за октябрь без дублей",
  "steps": [
    {
      "id": 1,
      "what": "Выбрать отклики за октябрь",
      "accept": "строк больше 0, пустых client_id 0",
      "writes": null,
      "status": "не пройден",
      "evidence": null
    },
    {
      "id": 2,
      "what": "Оставить первый отклик клиента по кампании",
      "accept": "строк после меньше или равно строк до; дублей по (client_id, campaign_id) 0",
      "writes": null,
      "status": "не пройден",
      "evidence": null
    },
    {
      "id": 3,
      "what": "Сохранить результат",
      "accept": "таблица существует, число строк совпадает с шагом 2",
      "writes": "<ПРЕФИКС_АГЕНТА>_responses_oct",
      "cell_hash": "<хеш одобренной ячейки>",
      "status": "не пройден",
      "evidence": null
    }
  ],
  "stop_after": [2]
}
```

Правила плана:
- У каждого шага есть проверяемый критерий приёмки `accept`.
- Модель может менять в плане только `status` и `evidence`, и только вместе. Остальное меняет владелец. Это проверяет код (К13).
- Шаг с записью указывает таблицу в `writes` и хеш одобренной ячейки.
- `stop_after` — вехи: после этих шагов агент останавливается и ждёт владельца.

## Цикл шага

Один шаг за цикл.

1. Прочитай `plan.json` и `progress.md`.
2. Убедись, что результат прошлого шага на месте: таблица есть, число строк совпадает с записанным.
3. Возьми первый шаг со статусом «не пройден».
4. Сделай шаг (`blueprint/03-compute-pyspark.md`).
5. Проверь критерий приёмки по выводу из окружения.
6. Запиши `status` и `evidence` в план, строку в `progress.md`, коммит.

`progress.md` — короткий журнал задачи: что сделано, что дальше, что непонятно. Новая сессия начинает с него.

## Паспорт прогона

```yaml
run: 2026-11-18-night
profile: night
until: "06:30"
budget:
  tokens: без лимита      # ночное окно 18:00–09:00; вне окна — лимит из конфига
  parallel_sessions: <N>  # сколько ролей одновременно; kernel всё равно один
  max_steps_per_role: из файла роли  # против зацикливания
read: [<источники из списка задач>, база знаний, вики, трекер]
write:
  tables: [<таблицы из поля «Запись» задач владельца>]
  files: [<рабочая папка прогона>]
tools: [<белый список>]
web: ограниченный  # К1
```

Агент паспорт не расширяет, субагенты его наследуют (К16). Лимиты проверяются внутри работы роли, а не только между этапами: превышение — остановка, а не предупреждение. Неограниченные токены ночью не отменяют лимитов шагов и времени: они ловят зацикливание.

## Когда что-то пошло не так

| Ситуация | Что делает агент |
|---|---|
| Шаг не прошёл приёмку | одна попытка исправить; не вышло — шаг «остановлен», причина в отчёт, следующая задача |
| Нужно одобрение, владельца нет | запрос в очередь; останавливается только эта задача |
| Кончился бюджет или время | остановка; «не завершено, причина» |
| Слот вычислений занят или kernel не стартует | работа без вычислений; повторная попытка в следующем цикле |
| Непонятна задача | `НУЖНО УТОЧНИТЬ`, задача пропускается |
| Правило мешает задаче | остановка шага; номер правила и безопасный вариант в отчёт |

После трёх неудачных попыток одного и того же агент не пробует четвёртый раз, а пишет, что пробовал и почему не вышло.

## Утренний отчёт

Порядок фиксированный: сначала то, что требует владельца.

1. **Ждёт решения:** одобрения, противоречия в базе знаний, `НУЖНО УТОЧНИТЬ`.
2. **Сделано:** задачи, закрытые шаги, ссылки на таблицы и файлы, ключевые числа.
3. **Не сделано и почему.**
4. **Черновики планов** по самостоятельно выбранным задачам.
5. **Отказы политики** за ночь: что агент пытался сделать и что было запрещено.
6. **Цифры:** время, токены, вызовы инструментов, по этапам.
